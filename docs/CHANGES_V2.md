# 통합 수정 요청서 반영 — 차이 분석과 설계 (v2)

> ✅ **반영 완료** (1~6단계). 실제 Supabase·운영 빌드·배포 사이트에서 자동 테스트와 브라우저 점검을 마쳤습니다.
> 마이그레이션 008~011 은 Supabase 에 적용되어 있습니다.

기존 1차 구현(1~8단계)을 기준으로, 통합 수정 요청서와 **다른 부분만** 정리했습니다.
요청서와 같은 부분(서버 판정, 4단계 사이클, 중복 방지, RLS, 실시간, 재접속 복구, 자동 기록 저장 등)은 그대로 유지합니다.

## 2. 행동 선언 → 5초 후 결과 공개 (8-3)

### 진행 구간 = 화면의 묶음 [턴 + 반응턴]
- 사이클 = 구간 A(1·2단계) + 구간 B(3·4단계)
- 한 구간의 두 단계에서 **행동 선언**이 모두 끝나면 → **5초 대기** → 구간 전체의 **판정 결과 공개** → 다음 구간 시작

예) 플레이어 선공
1. 1단계 플레이어 선공턴: 제한 시간 동안 행동 제출 → 시간 종료(또는 조기 판정) 시 **선언 공개**
   "A가 고블린을 공격했다." / "B가 회피를 시도했다."
2. 2단계 적군 반응턴: 적군이 즉시 **선언** — "고블린이 A를 공격했다."
3. ⏳ 5초 (화면에 "결과 공개까지 5…4…" 표시)
4. **판정 결과 공개**: 공격력·회피 성공 여부·피해량·HP 변화·사망·도주
5. 3단계로 진행

예) 적군 선공: 1단계 적군 선언 → 2단계 플레이어 반응(제한 시간, 다가오는 공격을 보고 회피/도망 선택) → 선언 공개 → 5초 → 결과

### 서버 처리 방식 (결과가 미리 새지 않게)
- 판정(무작위 공격력, 회피·도주 확률, 피해 계산)은 **결과 공개 시각이 된 순간 서버에서 처음 실행**합니다.
  그 전에는 결과가 DB 어디에도 없으므로 화면·네트워크로 새어 나갈 수 없습니다.
- 공개 시각(`battle_phases.reveal_at`)은 DB에 저장 → 새로고침해도 남은 시간 유지. 브라우저 시계로 결정하지 않음.
- 서버 예약 작업이 **1초마다** 확인 + 접속 중인 브라우저가 공개 시각에 확인 요청(서버가 시각을 다시 검사) → 약 5초에 공개.
- 결과 공개 전에는 다음 단계로 넘어가지 않음. 관리자 조기 판정도 "선언"만 앞당기고 5초 대기는 그대로.
- 강제 종료하면 대기 중인 결과 공개는 취소(판정하지 않음).

### 판정 순서 (기존 규칙 유지)
- 플레이어가 먼저 행동하는 구간: 도주 → 아이템 → 공격 → 적군 반격(직전에 회피를 고른 플레이어는 회피 판정)
- 적군이 먼저 행동하는 구간: 도주 → 적군 공격 적용(회피 판정) → 아이템 → 공격
- 결과 공개 시점에 이미 쓰러진 적군의 공격, 이미 쓰러진 대상에 대한 공격은 무효로 기록

### 로그
- `battle_logs.stage`: `declare`(행동 선언) / `result`(판정 결과) / `info`(그 외)
- 화면: 사이클 → [턴 + 반응턴] → "행동 선언" / "판정 결과" 두 묶음
